# دليلُ نشرِ بطاقةِ التذكرةِ من مسارِ الـ API — DEC-26

**التاريخ:** 2026-10-01
**البند:** DEC-26 (تنشيطُ دَينٍ مُعلَنٍ)
**ADR:** [0223](../../adr/0223-support-ticket-api-card-publishing.md)

## ما الدَّينُ الذي نُنشِطُه

`intake.ts` يُعلِنُ: «لا تُرفِقُ ملفاً ولا تُرسِلُ إشعاراً: كما كانَ، دَينٌ
مُعلَنٌ». مسارُ الـ API كانَ يفتحُ التذكرةَ ولا ينشرُ بطاقتَها في قروبِ الدعم.

## ما الذي بُنِيَ

1. **`card?: PostDisputeCardDependencies`** أُضيفَ إلى `SupportRouteDependencies`
   — اختياريٌّ، غيابُهُ لا يُعطِّلُ المسارَ.
2. **`postDisputeCard`** يُستدعى بعدَ فتحِ التذكرةِ في مسارَي الراكبِ والسائقِ.
3. **`container.supportCard`** يُكشَفُ من الحاويةِ — نفسُ `supportCore.card` الذي
   يستخدمهُ حوارُ البوتِ لا نسخةٌ ثانيةٌ.
4. فشلُ النشرِ لا يُلغي التذكرةَ — يُسجَّلُ السببُ في السجلِّ.

## الاختبارات

- `tests/unit/support-ticket-routes.test.ts` — أربعةُ اختباراتٍ جديدة:
  - نشرُ البطاقةِ بعدَ فتحِ تذكرةِ راكب.
  - نشرُ البطاقةِ بعدَ فتحِ تذكرةِ سائق.
  - 201 حتى لو فشلَ النشرُ — التذكرةُ قائمة.
  - يعملُ بلا `card` dependency — التذكرةُ تُفتَحُ ولا تُنشَرُ بطاقتُها.
- جميعُ الاختباراتِ تُجتازُ: ٦٤٨٩ ناجح، ٠ فاشل.

## القيودُ المُعلَنة

- **لا يُثبِتُ أنَّ البطاقةَ تصلُ فعلًا**: النشرُ يُختبَرُ بالوحدةِ، لا بالإنتاج.
- **لا يحكمُ في ازدواجِ النشر**: إن فُتِحَت تذكرةٌ من البوتِ والـ API معًا،
  قد تنشرُ بطاقتانِ — وهذا دَينٌ مُعلَنٌ يحتاجُ مُوثِّقًا مركزيًّا.
