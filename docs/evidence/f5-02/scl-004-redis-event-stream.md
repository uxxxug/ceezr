# دليل SCL-004 — مجرى أحداث مشترك عبر Redis Streams

**البند:** SCL-004  
**المرحلة:** F5-02  
**التاريخ:** 2026-09-08  
**الدرجة:** مُختبَر  

## المشكلة

ناقلُ الأحداث كان في العملية وحدها (`packages/infrastructure/tracking/event-bus.ts`). كلُّ نسخةٍ لها ناقلها، فلا تتبادل النسخُ الأحداث. حدثٌ يُنشر في نسخةٍ لا يصل مشتركي النسخ الأخرى.

## الحل

مجرى أحداثٍ مشتركٌ عبر Redis Streams (`packages/infrastructure/tracking/redis-event-stream.ts`):

- **النشر:** كلُّ حدثٍ يُضاف إلى Stream بـ`XADD` بعد تسليمه محليّاً.
- **الاستهلاك:** كلُّ نسخةٍ تستهلك من الـStream بـ`XREADGROUP` مع مجموعة مستهلكين باسم النسخة.
- **منع التسليم المزدوج:** كلُّ حدثٍ يُنشر محليّاً يُسجَّل معرّفُه في مجموعةٍ صغيرة (٢٠٠)، فإذا قرأه المستهلك ورآه فيها تخطّاه — فقد سُلِّم محليّاً.
- **لا حلقة:** المستهلك يُسلّم أحداث النسخ الأخرى للناقل المحليّ مباشرةً (لا يُضيفها إلى Redis ثانيةً).
- **الإغلاق الرشيق:** الـcontainer يحتفظ بـstop handle ويوقفه عند الإغلاق.

## لماذا Redis Streams لا Pub/Sub

Upstash عبر REST فقط: `SUBSCRIBE` اتصالٌ دائم لا يُمثَّل في REST (ADR-0016). و`XADD`/`XREAD` طلبٌ/استجابةٌ في كلِّ نداء HTTP.

## الربط في الحاوية

`apps/gateway/src/container.ts`:
- عند توفر Redis: يُنشئ `RedisTrackingEventStream` ويُغلّف `trackingBus.publish` ليُضيف إلى Redis بعد التسليم المحليّ.
- يبدأ مستهلكاً يُسلّم أحداث النسخ الأخرى للناقل المحليّ.
- يوقف المستهلك عند الإغلاق الرشيق.
