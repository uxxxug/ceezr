# ADR 0223 — نشر بطاقة التذكرة في قروب الدعم من مسار الـ API

**التاريخ:** 2026-10-01
**الحالة:** مقبول — منفَّذ

## السياق

`intake.ts` يُعلِنُ صراحةً: «لا تُرفِقُ ملفاً ولا تُرسِلُ إشعاراً: كما كانَ، دَينٌ
مُعلَنٌ». حين يفتحُ راكبٌ أو سائقٌ تذكرةَ دعمٍ من داخلِ التطبيقِ المصغَّرِ عبر
`POST /v1/support/tickets` أو `POST /v1/driver/support/tickets`، كانت التذكرةُ
تُفتَحُ في القاعدةِ ولا تصلُ بطاقتُها إلى قروبِ الدعمِ — فلا يعرفُ الفريقُ أنَّ
هناكَ تذكرةً تنتظرُه. حوارُ البوتِ كانَ ينشرُ البطاقةَ عبرَ `postDisputeCard`، لكنَّ
مسارَ الـ API كانَ يفتحُ التذكرةَ ويرجعُ المرجعَ دونَ نشرٍ.

## القرار

نُمرِّرُ `PostDisputeCardDependencies` نفسَها التي يستخدمُها حوارُ البوتِ إلى
مسارِ الـ API، ونستدعي `postDisputeCard` بعدَ فتحِ التذكرةِ مباشرةً. فشلُ النشرِ
لا يُلغي التذكرةَ المفتوحةَ — التذكرةُ قائمةٌ في القاعدةِ، والبطاقةُ لم تصلْ،
ويُسجَّلُ السببُ في السجلِّ.

## العواقب

- **إيجابيّة:** تذاكرُ الـ API تصلُ إلى فريقِ الدعمِ كما تصلُ تذاكرُ البوتِ. مصدرُ
  نشرٍ واحدٌ لا نسخةٌ ثانيةٌ (القاعدةُ 0.6).
- **سلبيّة:** استدعاءٌ إضافيٌّ لقراءةِ السياقِ والنشرِ في كلِّ فتحِ تذكرةٍ من
  الـ API. لكنَّهُ استدعاءٌ واحدٌ لا متواليّةٌ، والتأخيرُ مقبولٌ لتذكرةِ دعمٍ.
- **محايدة:** غيابُ `card` لا يُعطِّلُ المسارَ — التذكرةُ تُفتَحُ ولا تُنشَرُ
  بطاقتُها، وهوَ السلوكُ السابقُ تماماً.
