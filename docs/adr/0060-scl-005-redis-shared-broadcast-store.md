# ADR-0060 — مخزنُ البثّ المشترك لـ`SCL-005`: Redis key + ادّعاءٌ ذرّيٌّ لبدءِ البثّ

- **الحالة**: مقبول — `SCL-005` (القسم 11-ب).
- **يبني على**: ADR-0058 (ناقلُ Redis Streams `SCL-004`)، ADR-0016 (الناقل في العملية + الموقع الحيّ).
- **يُلغي جزءًا من**: ADR-0016 §«خريطة `tripId→messageId` في الذاكرة» وحدها — لا الموقع الحيّ ولا الخنط ولا بوّابة الترتيب.

## السياق

المُرحِّلُ (`customer-live-relay.ts`) كانَ يخزنُ `tripId → Broadcast` في `Map` داخلَ
العمليةِ. كلُّ بثٍّ مفتوحٍ يحملُ `messageId` (رسالةُ Live Location في تلغرام) و`chatId` و
`sessionId`/`lastAppliedSeq` (بوّابةُ الترتيبِ `BUG-009`) و`sentAtMs`/`lat`/`lng` (الخنطُ
بالزمنِ والمسافةِ). والخريطةُ مصدرُ الحقيقةِ الوحيدُ لهذه المعرّفات.

والعيبُ مزدوجٌ:

1. **إعادةُ التشغيلِ تُفقدُ المعرّفات** — فأوّلُ إصلاحةٍ بعدَ النشرِ تفتحُ رسالةَ بثٍّ
   ثانيةً في محادثةِ العميلِ، والأولى تسكنُ حتى تنتهيَ مدّتُها. وهو عيبٌ تجميليٌّ يظهرُ
   عندَ النشرِ فقط (والنشرُ يوقفُ الجلساتِ أصلاً)، لكنّه عيبٌ حقيقيٌّ متعدّدُ النسخِ.
2. **النسخُ المتعدّدةُ لا تشاركُ الحالة** — بعدَ `SCL-004` (المجرى المشترك عبر Redis
   Streams)، صارَ في وسعِ نسختَينِ أن تريا الحدثَ الأولَ لرحلةٍ معاً. فلو لم تُسلسَلْ
   لفتحتا رسالتَي بثٍّ في محادثةِ العميل.

ونصُّ حلّ `SCL-005` صريحٌ في `ROADMAP`: «جدول/مفتاح مشترك، أو إسقاطُ الحاجةِ كليّاً بعدَ
انتقالِ التتبّع إلى Mini App». والمسارُ الثاني (`F4-07`) مستقبليٌّ (`[ ]`) — يعتمدُ
انتقالَ Mini App الذي لم يُنجَز. فلا يُغلَقُ `SCL-005` بـ«التزامٍ مستقبليٍّ»: إغلاقُه
بالتزامٍ لا يُحقّقُ القيدَ بل يقلبُ حالةً بلا تحقق.

## ما فُحص فعلاً، وحكمُ كلٍّ منه

### ١. عمودٌ على `orders` — **مرفوضٌ لهذه الحاجة**

التعليقُ الأصليُّ في `customer-live-relay.ts` تنبّأَ بالحلّ: «أن يُقرأ معرّفُ الرسالةِ من
`orders` لا من جدولٍ جديد». لكنّ `messageId` مقبضٌ عابرٌ لقناةِ تلغرام لا حقيقةُ مجالٍ
دائمة: له TTL طبيعيٌّ يزولُ فيه من تلقاءِ نفسِه، وسيُحذفُ كليّاً مع `F4-07`. وعمودُ
`orders` يطلبُ هجرةً (`check-migrations`) ومعاملةً حولَ نداءِ تلغرام الخارجيّ. والقاعدةُ
ليست مصدرَ الحقيقةِ لهذا المقبضِ — تلغرام هو.

### ٢. Redis key مشترك — **مقبولٌ (المُعتمَد)**

Redis يطابقُ «مفتاحٌ مشترك» بلا تعديلٍ حوكميٍّ للنصّ (`ح-1`). والمفتاحُ يمنحُ:

- **مشاركةً بينَ النسخِ**: نسختانِ تقرآنِ الحالةَ نفسَها فيُعدِّلانِ الرسالةَ نفسَها لا
  تفتحانِ رسالةً جديدة.
- **بقاءً بعدَ إعادةِ التشغيلِ**: الحالةُ تبقى في Redis حتى انتهاءَ TTL، فلا تُفتحُ رسالةٌ
  ثانيةٌ عندَ النشرِ.
- **ادّعاءً ذرّيّاً لبدءِ البثّ**: `SET NX` يمنحُ نسخةً واحدةً حقَّ البدء؛ والأخرى تتخطّى،
  فيلتقطُ الحدثُ التالي الحالةَ فيُعدِّلُها.

والكتابةُ عندَ البدءِ والإغلاقِ لا عندَ كلِّ إصلاحةٍ — فيتفادّى ثمنَ الكتابةِ لكلِّ
تحديثٍ (الذي كانَ دافعَ التعليقِ الأصليِّ للرفض).

### ٣. إسقاطُ الحاجةِ كليّاً (`F4-07`) — **مستقبليٌّ، لا يُغلَقُ به الآن**

`F4-07` (إسقاطُ تعديلِ رسالةِ Live Location كمسارٍ أساسيٍّ بعدَ انتقالِ Mini App)
`[ ]` لم يُنجَز. فالحاجةُ لم تُسقَطْ بعدُ. وهذا التنفيذُ لا يمنعُ `F4-07` — بل
يُسهِّلُه: متى انتقلَ التتبّعُ إلى Mini App، يُحذفُ المخزنُ كليّاً (مفتاحٌ عابرٌ بلا
هجرةٍ، لا عمودُ قاعدةٍ يُترَكُ معطّلاً).

## القرار

1. **واجهةُ تطبيقٍ `LiveBroadcastStore`** في `application/tracking`: `get`/`save`/
   `delete`/`claimStart`/`releaseClaim`. التنفيذُ في الذاكرةِ (`createInMemoryLiveBroadcastStore`)
   للاختبارِ افتراضيّاً، وفي Redis (`createRedisLiveBroadcastStore`) للإنتاج.
2. **الادّعاءُ الذرّيُّ**: `claimStart(tripId, token, ttl)` بـ`SET key token NX PX ttl` —
   ينجحُ مرّةً واحدةً فقط. والتحريرُ بـLua (`if get == token then del`) آمنٌ ضدَّ الإطلاقِ
   الخاطئ.
3. **إعادةُ هيكلةِ المُرحِّلِ**: استبدالُ `Map` بالمخزنِ المُحقَن. وبدءُ البثّ صارَ يُدّعى
   ذرّيّاً: إن نجحَ الادّعاءُ نادى `channel.start` وحفظَ الحالة؛ وإلّا تخطّى (الحدثُ التالي
   يلتقطُ الحالةَ). والكتابةُ عندَ البدءِ والإغلاقِ والتشوهِ فقط لا لكلِّ إصلاحة.
4. **التوصيلُ في `container.ts`**: Redis حين يكونُ متاحاً (`sessionStore === "redis"`)،
   وإلّا الذاكرةُ (تنازلٌ موثَّقٌ كنشرِ نسخةٍ واحدةٍ). و`newClaimToken: () =>
   crypto.randomUUID()` يُحقَنُ حتى لا تستوردَ طبقةُ التطبيقِ `node:crypto` مباشرة.

## العواقب

- **إيجابيّة**: الحالةُ مشتركةٌ بينَ النسخِ وتبقى بعدَ إعادةِ التشغيلِ. والادّعاءُ الذرّيُّ
  يمنعُ رسالتَي بثٍّ متزامنتَين. ولا هجرةَ مخطَّط (مفتاحٌ عابرٌ بـTTL). ولا تعديلُ نصِّ
  حلّ (`ح-1` — «مفتاحٌ مشترك» موجودٌ في النصّ).
- **سلبيّة**: اعتمادٌ على Redis لكلِّ بثٍّ مفتوح. والإخفاقُ يُسجَّلُ لا يُسقِطُ (العرضُ نقطةٌ
  واحدةٌ تُستبدَلُ بأحدثِ ما وصل، والحدثُ التالي يُعيدُ المحاولة). وحينَ لا يكونُ Redis
  متاحاً يتنازلُ إلى الذاكرةِ (نشرُ نسخةٍ واحدةٍ) — موثَّقٌ لا صامتٌ.
- **محايدة**: `openBroadcasts` صارَ عدّاداً محليّاً (هذه النسخةُ وحدَها) لا عالميّاً — وهذا
  صحيحٌ للقياسِ في نظامٍ موزَّع.
